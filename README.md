# ВышКат — учёт парка кикшеринга

Домашнее задание №1 по курсу «Конструирование программного обеспечения»: консольное
приложение учёта парка сервиса «ВышКат». Условие — в файле `КПО-ДЗ-1-кикшеринг-ВШЭ.pdf`.

## Установка и запуск

Добавлен Makefile для удобства, чтобы посмотреть команды:

```bash
make
```

Для запуска необходим [uv](https://docs.astral.sh/uv/getting-started/installation/).
Первый запуск:

```bash
make install
make run
```

## Использование

Приложение читает текстовые команды: с клавиатуры (`make run`) или из файла
(`uv run vyshkat <файл>`). Демонстрация всех сценариев — `make demo`, сценарий лежит в
[`scenarios/demo.txt`](scenarios/demo.txt).

| Команда | Что делает |
|---|---|
| `accept <вид> "<название>" simplicity=N condition=N [energy=X]` | принять технику; перед приёмкой — техосмотр |
| `add <вид> "<название>" [energy=X]` | поставить вещь на баланс, без осмотра |
| `report` | число единиц (всего, техника / вещи, по видам) и суточный расход энергии |
| `newbies` | техника, которую можно выдавать новичкам |
| `inventory` | номера, виды и наименования всего на балансе |
| `kinds` | виды и их параметры: техника `scooter`, `ebike`, `bicycle`; вещи `helmet`, `dock`, `cabinet` |
| `help`, `exit` | справка, выход |

Параметры пишутся как `ключ=значение` в любом порядке, дробные — через точку. Название с
пробелами — в кавычках; знак `=` в названии не поддерживается. Строки с `#` — комментарии.

```
> accept scooter "Ninebot Max G30" simplicity=7 condition=8 energy=0.45
Принят: INV-0001 Электросамокат «Ninebot Max G30»
> accept scooter "Xiaomi M365" simplicity=8 condition=3 energy=0.3
Отказ: Электросамокат «Xiaomi M365» — состояние 3/10 ниже порога 5
> add helmet "Шлем M"
Поставлен на баланс: INV-0002 Шлем «Шлем M»
> accept bicycle "Stels" simplicity=15 condition=5
Ошибка: simplicity=15 — простота: ожидается от 1 до 10, получено 15
> inventory
INV-0001  Электросамокат  Ninebot Max G30
INV-0002  Шлем            Шлем M
```

Ошибка ввода не останавливает работу: приложение сообщает о ней и ждёт следующую команду.

## Доменная модель

Код: `src/vyshkat/domain/`.

| Тип | Что это | Потребляет энергию |
|---|---|---|
| `Vehicle`: `Scooter`, `EBike`, `Bicycle` | Прокатный транспорт: название, простота для новичка (1–10), техсостояние (1–10) | `Scooter`, `EBike` |
| `Thing`: `Helmet`, `DockStation`, `ChargingCabinet` | Вещи на балансе | `DockStation`, `ChargingCabinet` |
| `InventoryItem(number, asset)` | Актив, принятый на баланс | — |

Абстракции из задания — протоколы в `protocols.py`:

- `EnergyConsumer` — суточный расход энергии, кВт·ч;
- `Inventoried` — строка инвентарной ведомости: номер, вид, наименование; его реализует
  `InventoryItem`. Состав протокола задаёт его потребитель — отчёт по номерам (ISP).

**Почему номер не в самом самокате.** У предложенного к приёмке объекта номера нет вообще:
он появляется только при постановке на баланс, вместе с обёрткой `InventoryItem`. Если бы
номер был полем `Scooter`, то до приёмки он был бы пустым или выдавался бы до техосмотра и
сгорал при отказе.

## Приёмка

Код: `src/vyshkat/services/`.

```
accept_vehicle(vehicle) ─► ServiceCenter.inspect(vehicle)
                             ├─ отказ ─► Rejected(reason), номер не выдаётся
                             └─ годен ─► номер INV-NNNN ─► InventoryItem ─► Fleet ─► Accepted(item)

add_thing(thing) ──────────────────────► номер INV-NNNN ─► InventoryItem ─► Fleet ─► Accepted(item)
```

- `ServiceCenter` — протокол техосмотра. Реализация `ConditionServiceCenter` принимает
  транспорт с техсостоянием не ниже порога (по умолчанию 5).
- `InventoryNumberGenerator` — одна серия номеров на технику и вещи.
- `Fleet` — записи на балансе; повторный номер отклоняется.

## Отчёты

`FleetReports` (`services/reports.py`) строит отчёты только по тому, что стоит на балансе:

| Отчёт | Как считается |
|---|---|
| Число единиц | всего, техника / вещи, разбивка по видам |
| Суточный расход энергии | сумма по активам, которые являются `EnergyConsumer` |
| Техника для новичков | транспорт, который одобряет `NewbiePolicy`: простота ≥ 6 |
| Номера, виды и наименования | всё на балансе; отчёт видит записи только как `Inventoried` |

## DI-контейнер

Composition root — `src/vyshkat/container.py`, функция `build_container()`. Только здесь решается,
какая реализация стоит за абстракцией; остальные классы получают зависимости через конструктор
и про контейнер не знают.

| Регистрация | Время жизни | Почему |
|---|---|---|
| `Fleet`, `InventoryNumberGenerator` | один экземпляр на приложение | это состояние учёта: приёмка и отчёты должны видеть один парк и одну серию номеров |
| `ServiceCenter` → `ConditionServiceCenter` | новый при каждом запросе | без состояния |
| `NewbiePolicy`, `AcceptanceService`, `FleetReports` | новый при каждом запросе | без собственного состояния, общее берут из одиночек выше |

Подмена техосмотра в тестах (`tests/test_container.py`): поверх готового контейнера
регистрируется фейк, и приёмка, полученная из контейнера, осматривает уже через него:

```python
container = build_container()
container.register(ServiceCenter, instance=FakeServiceCenter(Verdict(False, "...")))
container.resolve(AcceptanceService)  # внутри — фейк
```

## Расширение: новый вид техники или вещи

Например, электроскутер:

1. **Домен** — класс-наследник в `domain/vehicles.py` (для вещи — в `domain/things.py`):

   ```python
   @dataclass(frozen=True)
   class EScooter(Vehicle):
       daily_energy_kwh: float
       kind: ClassVar[str] = "Электроскутер"

       def __post_init__(self) -> None:
           super().__post_init__()
           require_positive("daily_energy_kwh", "суточный расход", self.daily_energy_kwh)
   ```

2. **Консоль** — строка в `VEHICLE_KINDS` (для вещи — в `THING_KINDS`) в `cli/catalog.py`:
   имя для команды, фабрика из параметров и подсказка по параметрам.

## SOLID

| Принцип | Где | Почему так |
|---|---|---|
| **S** — одна причина для изменения | `domain/*` — инварианты объектов; `ServiceCenter` — правило техосмотра; `InventoryNumberGenerator` — формат номеров; `Fleet` — хранение; `AcceptanceService` — порядок приёмки; `FleetReports` — отчёты; `NewbiePolicy` — правило для новичков. Консоль разбита так же: `parser` — разбор строки, `catalog` — слова → объекты, `app` — команды → сервисы, `runner` — цикл ввода, `main` — запуск и кодировка | Смена порога осмотра, формата номера или текста ответа затрагивает ровно один модуль |
| **O** — открыт для расширения, закрыт для изменения | Новый вид = класс-наследник + строка в `cli/catalog.py` (см. «Расширение»). Приёмка, парк и отчёты работают с `Vehicle`, `Thing` и протоколами, а не с видами | Добавление вида не трогает ни одной строки сервисов |
| **L** — подстановка наследников | Любой наследник `Vehicle` проходит осмотр, учёт и отбор для новичков. Общие правила транспорта проверяются на каждом виде (`each_kind` в `tests/domain/test_vehicles.py`); `FakeServiceCenter` подставляется вместо `ConditionServiceCenter` без изменений в `AcceptanceService` | Наследники только добавляют поля и проверки, ничего не ослабляют |
| **I** — узкие интерфейсы | `EnergyConsumer` отдельно от `Vehicle` и `Thing`: велосипед и шлем его не реализуют, док-станция и шкаф — да. `Inventoried` — ровно то, что нужно отчёту по номерам (номер, вид, наименование), а не весь `InventoryItem`. У `ServiceCenter` один метод | Никто не зависит от того, чем не пользуется |
| **D** — зависимость от абстракций | `AcceptanceService` получает `ServiceCenter` (протокол), а не `ConditionServiceCenter`. Реализации выбирает только composition root — `container.py`; остальные классы получают зависимости через конструктор и о контейнере не знают | Правило техосмотра меняется регистрацией в контейнере, тесты подставляют фейк |

## Ответы на обязательные вопросы

**Какой принцип SOLID применён наиболее явно и где?**
DIP вокруг техосмотра. `AcceptanceService` (`services/acceptance.py`) зависит от протокола
`ServiceCenter` (`services/service_center.py`); реализация `ConditionServiceCenter`
назначается в `container.py`. Это видно и в коде, и в тестах: техосмотр подменяется фейком
через конструктор (`tests/services/test_acceptance.py`) и через контейнер
(`tests/test_container.py`, `tests/cli/test_app.py`).

**Какой принцип сознательно ограничен и почему это приемлемо?**
DIP — для `NewbiePolicy`, `Fleet` и `InventoryNumberGenerator`. Это конкретные классы без
интерфейсов: реализация у каждого одна, второй не предвидится, а в тестах используются
настоящие — они детерминированы и быстры. Интерфейс с единственной реализацией был бы
декоративным. Если появится второе правило для новичков, `NewbiePolicy` выносится в протокол
так же, как `ServiceCenter`, — `FleetReports` при этом не меняется.

Обратный случай — `Inventoried`: у протокола тоже одна реализация (`InventoryItem`), но он
оставлен. Его прямо требует задание, и он сужает то, что видит отчёт по номерам (ISP); цена в
Python — несколько строк `Protocol`.

**Что сломается (или нет) при расширении?**

- *Новый вид транспорта или вещи* — ничего: класс в домене и строка в каталоге, подробно в
  разделе «Расширение». Новый вид сам попадёт в отчёты.
- *Сотрудник службы эксплуатации* — ничего. По заданию сотрудники не стоят на балансе, поэтому
  сотрудник — не `Asset` и не `Inventoried`: свой модуль, своё хранилище. Если осмотр начнёт
  проводить конкретный сотрудник, это новая реализация `ServiceCenter`; `AcceptanceService`
  не меняется.
- *Склад запчастей* — зависит от модели. Если запчасть — вещь с инвентарным номером, это новые
  наследники `Thing`, как выше. Если это третья категория активов в `Asset = Vehicle | Thing`,
  сломается немного, но решать придётся в двух местах: путь приёмки (новый метод в
  `AcceptanceService`, рядом с `accept_vehicle` и `add_thing`) и подсчёт в
  `FleetReports.unit_counts`. Подсчёт категорий явный, поэтому новая категория не попадёт в
  «вещи» молча, а будет видна как `total ≠ vehicles + things`. Номера, `Fleet`,
  `InventoryItem`, расход энергии и отчёт по номерам изменений не требуют. Если запчасти
  учитываются количеством, а не поштучно, — это отдельный агрегат `Warehouse`, который парк и
  номера не затрагивает.

**Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется
зависимость?**

| Что фиксирует | Тест |
|---|---|
| Порог осмотра: 5 и 10 принимаются, 1 и 4 — нет | `tests/services/test_service_center.py` |
| Приёмка выполняет решение осмотра: одобренный получает номер и попадает в парк, отклонённый — нет и номер не тратит, вещь не осматривается | `tests/services/test_acceptance.py` |
| Подмена через DI: поверх `build_container()` регистрируется `FakeServiceCenter`, и приёмка из контейнера отклоняет самокат в состоянии 10/10 | `tests/test_container.py::test_service_center_is_replaced_through_container`, `tests/cli/test_app.py::test_accept_uses_service_center_from_container` |
| Правило для новичков: простота 6 и 10 подходят, 1 и 5 — нет | `tests/services/test_newbie_policy.py` |
| Отчёт берёт только транспорт и использует внедрённую политику | `tests/services/test_reports.py::test_newbie_vehicles_follow_policy_and_skip_things`, `::test_newbie_vehicles_use_injected_policy` |

`FakeServiceCenter` (`tests/fakes.py`) — обычный класс: выносит заданный вердикт и запоминает,
кого осматривал. mypy проверяет, что он соответствует протоколу `ServiceCenter`.

## Роль ИИ

Большая часть тестов и файлов без кода (README, Makefile), а также некоторые куски кода написаны с
Claude в режиме совместной разработки. Коммиты делались только после моей проверки. Все решения по
моделям, связям между сущностями и другими архитектурными вопросами приняты мной.

Решения, принятые мной:

- архитектура модели: номер живёт только в обёртке `InventoryItem`, у вещи до приёмки номера
  нет вообще; два пути приёмки (`accept_vehicle` / `add_thing`); `inspect` принимает `Vehicle`;
- стек и инфраструктура: uv, Makefile по образцу своего проекта, pre-commit хук с тестами,
  порог покрытия;
- консоль: доступные команды и поведение

Переработано мной:

- accept и add 2 разные команды, а не один вход на всё
- явный подсчёт техники и вещей в `unit_counts` вместо «всё, что не транспорт, — вещи»;
- исправил вывод на Windows, выделил `DomainError` из голого `ValueError`,
  сообщения об ошибках в терминах пользователя;
- Makefile по моему шаблону образцу своего проекта;
- тексты README, Makefile и комментарии в коде сокращены или написаны более понятно.
